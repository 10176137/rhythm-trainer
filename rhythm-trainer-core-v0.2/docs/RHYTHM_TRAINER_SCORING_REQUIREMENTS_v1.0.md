# Rhythm Trainer — 评分引擎需求规格说明书 v1.0

- 版本：1.0.0
- 状态：开发基线 / 可交给 Zcode 拆解实现
- 产品形态：本地优先的钢琴练习工作台
- 技术基线：React + TypeScript + Vite 前端；Rust Core 作为评分与诊断唯一权威实现；MIDI 设备适配器可由 Web MIDI 或 Node 原生层提供
- 核心目标：不仅判断“弹对了多少”，还要能解释整首曲子、任意小节/片段为什么弹得不稳，并给出可执行的下一步练习建议。

---

## 1. 产品目标与非目标

### 1.1 产品目标

用户连接 MIDI 键盘并导入 MusicXML 乐谱后，系统应能够：

1. 将乐谱转成可计算的目标事件，并保留小节、拍位、声部、谱表、连音线等信息。
2. 采集实际演奏，可靠地区分按键开始、按键释放、踏板等事件。
3. 将演奏事件与乐谱事件对齐；即使漏音、错音、多音、重复音，也不能导致后续整段错位。
4. 评价音高准确度、起音时机、节奏稳定性、按键时长、连续性和演奏完整度。
5. 同时提供整曲、左右手/声部、小节、任意选区、单音级别的报告。
6. 明确区分“整体偏早/偏晚”“局部忽快忽慢”“持续渐快/渐慢”“音符漏弹/错弹”“按键时长不合适”。
7. 为每个结论提供可追溯证据、样本量和置信度；数据不足时明确说“不足以判断”，不编造精确分数。
8. 支持慢速练习、分段循环、节拍器、达标后逐级提速，以及原速迁移测试。
9. 相同输入、相同配置和相同算法版本必须产生可重复的结果。
10. 支持录制会话回放、问题定位、报告导出和算法回归测试。

### 1.2 非目标 / 明确边界

- MIDI 不等于真实声学录音。仅凭 MIDI 不评估音色、踏键触感、手型、手腕动作或真正的声学音量。
- 不把“弹完整首的总时长”当作节奏评分的替代品。
- 不把所有音符都要求按住理论时值的 100%；必须考虑连音线、断奏、演奏模式和踏板。
- 不宣称分数是绝对的音乐审美评价。分数用于可解释的练习反馈。
- v1.0 不要求 AI 大模型参与实时评分。规则、指标和诊断由 Rust Core 确定性地产生；未来 AI 只能基于结构化证据生成解释/练习计划，不能改写事实数据。
- 不强制微服务化，不为尚无业务需要的规模预先引入复杂分布式架构。

## 2. 用户流程

1. 创建练习会话，选择设备或模拟器。
2. 导入 MusicXML；解析并展示曲目、拍号、调号、速度标记、小节数、声部与可识别的谱面特性。
3. 选择练习模式、目标速度、左右手/声部、评分严格度和是否评估按键时长。
4. 校验 MIDI 输入：设备、通道、时钟、输入延迟、踏板能力；可运行简短校准。
5. 练习中显示当前小节、目标拍位、实时事件状态、错音/漏音/节奏偏差；实时分数应标记为暂定值。
6. 结束或暂停后，运行完整对齐和评分，生成报告。
7. 报告可切换整曲、小节、声部和自定义区间；点击问题项可定位到乐谱位置和事件时间线。
8. 系统建议最值得练的 1–3 个片段，支持一键建立分段循环练习。
9. 保存会话与算法版本，支持历史比较和导出。

## 3. 评分输入数据契约

评分分层处理，不允许前端自行成为第二套评分真相。

### 3.1 Raw MIDI Packet（原始输入层）

每个可读取的 MIDI 消息至少保留：

- `sessionId`
- `sourceId` / `sourceName`
- `sequenceNo`（每个来源单调递增；如来源无法提供则由适配器生成）
- `receivedAtMonotonicNs`（单调时钟）
- `receivedAtWallClockMs`（仅用于展示/跨日志关联）
- `rawBytes`
- `statusByte`、`channel`（若适用）
- `transport`（web-midi / node-midi / simulator）
- `parseStatus`（valid / unsupported / malformed）
- `adapterVersion`

要求：保留原始包可供诊断与确定性回放。原始数据不应在 UI 层被覆盖或修正。

### 3.2 Normalized MIDI Event（规范化事件层）

支持至少：

- note-on
- note-off
- control-change（含 CC64 sustain）
- pitch-bend
- program-change（可采集但 v1.0 不用于基本评分）
- channel-pressure / poly-aftertouch（可选采集，不作为必需评分项）
- realtime/unsupported event 的明确分类

规范化字段至少包括：

- `eventId`
- `sessionId`
- `sourceId`
- `sequenceNo`
- `timestampNs`（统一单调时间基准）
- `channel`
- `kind`
- `data1` / `data2`
- `parseWarnings`

MIDI Note On 且 velocity=0 必须规范化为 Note Off。不得因来源设备不同而改变这一语义。

### 3.3 Key Lifecycle（按键生命周期）

将 Note On/Off 配对成 `PerformedNote`：

- `performedNoteId`
- `sourceId`、`channel`、`pitch`
- `onsetNs`
- `releaseNs`（允许为空）
- `heldDurationNs`（仅在有效配对时计算）
- `onsetVelocity`、`releaseVelocity`（release velocity 若无则为空）
- `pairingStatus`：paired / missing-release / orphan-release / ambiguous
- `sourceEventIds`
- `qualityFlags`

配对键不能只使用 pitch；至少考虑 source + channel + pitch，并处理同音重复按下、重叠同音和设备异常。不能确定唯一配对时应标记 ambiguous，而不是静默合并。

### 3.4 Sustain / Pedal

- CC64 状态必须独立建模，不可把踏板保持时间误当作物理按键时长。
- 物理按键时长始终是 `Note Off - Note On`。
- v1.0 可报告踏板使用事件与覆盖区间，但若乐谱踏板标记解析不完整，不能给出严格踏板正确率。
- 若输入源没有踏板数据，报告必须显示“未采集”，不能显示为零错误。

### 3.5 时间与时钟

- 核心评分使用单调时钟；墙上时间只用于显示。
- 不同适配器必须提供其时间精度/来源说明。
- 不允许用网络时间或 Date.now 的跳变直接计算音符时长。
- 输入延迟校准只允许估计设备/链路固定偏移；不能把真实演奏节奏偏差全部“校正掉”。
- 报告要区分 `estimatedInputLatencyMs`、`globalTimingBiasMs` 和局部节奏误差。

## 4. 乐谱模型与 MusicXML

解析器将 MusicXML 转为稳定的 `ScoreEvent` 列表。每个目标事件至少包含：

- `scoreEventId`
- `partId` / `partName`
- `staff` / `voice`
- `measureNumber`
- `beatPosition`（使用有理数或精确分数，避免浮点累计误差）
- `writtenDuration`
- `soundingPitch`（考虑移调乐器时须有明确策略）
- `tieGroupId` / tie 状态
- `articulation`（staccato、tenuto 等，若可解析）
- `isGraceNote`、`isRest`、`isChordTone`
- `tempoMapPosition` / 目标起音时间
- `parseConfidence` / `unsupportedFeatures`

要求：

1. 支持常见 4/4、3/4、6/8 等拍号、变速标记、附点、休止符、三连音、连音线、和弦、左右手/声部。
2. 节拍位置用精确有理数表示；绝对时间由 tempo map 统一计算。
3. 对无法可靠解析的复杂记谱（例如部分装饰音、复杂跨小节连音、非标准扩展）记录能力缺口，并降低对应指标置信度。
4. 连音线组默认视为一个连续发声目标，但实际物理按键策略可由模式配置：连续按住或重新触键；如果谱面无法确定，应避免硬性处罚。
5. 休止符是节奏结构的一部分；系统需检测休止期间意外起音，但要考虑可配置容忍窗。
6. 对和弦，支持同一拍位多个音符目标，并计算和弦完整度、起音离散程度；不能简单按单音线性序列误配。

## 5. 对齐引擎（Score ↔ Performance Alignment）

### 5.1 设计原则

- 对齐是全局/局部单调匹配，不是“每来一个 MIDI 音就与下一个谱面音比较”。
- 漏音、错音、多音、重复音不能让后续事件整体错位。
- 允许演奏速度偏离目标速度；速度偏离本身应体现在指标中，而不是直接导致对齐失败。
- 对齐必须可解释：每个匹配、漏音、额外音、错音都要有原因类别和代价。
- 允许用户选择评估声部/手；不能默认 MIDI channel=左手或右手。
- 和弦需要按拍位/时间簇匹配，支持轻微的指间起音差。

### 5.2 推荐实现

先按时间和拍位建立候选窗口，再使用带代价的单调动态规划或等价算法完成匹配。代价由以下因素构成：

- pitch mismatch
- onset time error / beat-position consistency
- duration mismatch（可选，不能过度影响对齐）
- part/voice/staff filter
- chord-cluster membership
- missing / extra penalty

对齐参数必须有版本号，结果保存算法版本和配置。实时阶段可以提供低延迟的暂定匹配，练习结束后以完整事件流重算最终报告。

### 5.3 失败与降级

- 对齐不确定时输出 `ambiguous` / `low-confidence`，不能强行给出高精度结论。
- 如果用户从中间开始演奏、跳过小节或重复段落，应提供可配置的起始小节和重复段落策略；v1.0 至少支持用户指定起始小节。
- 若乐谱解析或 MIDI 输入质量不足，应明确标出无法评分的指标和原因。

## 6. 评分指标定义

评分应先保留原始指标，再映射到 0–100 的可配置分数。原始指标比单一总分更重要。

### 6.1 音高与音符准确度

报告至少包括：

- 正确音符数、漏音数、额外音数、错误音高数
- 音符召回率 / 精确率（需说明定义）
- 和弦完整度
- 错音类型和位置
- 休止期间额外起音（单独列出）

必须避免把一个错误音符导致后续全部被判错。音符准确率的分母与过滤规则必须在报告中说明。

### 6.2 起音准确度（Onset Accuracy）

每个匹配音符：

`onsetErrorMs = actualOnsetMs - targetOnsetMs`

正值表示晚，负值表示早。至少计算：

- signed mean / median（整体偏早或偏晚）
- mean absolute error（平均绝对偏差）
- P50 / P90 绝对误差
- 在用户所选容忍窗之外的比例
- 分小节起音误差分布

必须分离固定输入延迟估计和真实演奏偏差。容忍窗应可配置，并按练习模式变化。

### 6.3 节奏稳定性（本产品核心指标）

不得以总时长替代节奏稳定性。必须至少计算：

1. **局部 IOI**：相邻目标起音间隔与实际起音间隔的偏差。对错音/漏音需基于匹配事件计算，不能把漏音直接当作超长节拍。
2. **局部速度比**：实际 IOI / 目标 IOI；1.0 表示一致，大于 1 表示实际更慢。
3. **局部抖动**：定义明确的稳健离散指标（例如绝对 IOI 比偏差的 MAD 或标准差），排除明显的匹配异常并披露样本数。
4. **速度漂移**：按小节/滑动窗口拟合速度比趋势，识别逐渐渐快/渐慢。
5. **节奏补偿**：检测前面弹快、后面弹慢而整体结束时间恰好正确的情况。
6. **分小节热力图**：显示偏快、偏慢、稳定或数据不足，并可点击查看证据。

对长休止、跨小节、重复音、和弦及漏音，应使用目标拍位归一化，不可盲目将所有相邻实际事件直接相减。

### 6.4 按键时长（Key Duration）

`heldDurationMs = releaseMs - onsetMs`

对齐成功且 Note On/Off 配对有效时才计算。报告至少包括：

- 目标时长、实际按键时长、时长差、时长比
- 过短/过长比例
- 分声部、小节和音符类型统计
- 未配对或不确定的音符数量

目标时长策略：

- `notation-strict`：按谱面时值、tempo map、tie 组计算，适用于明确标注的练习。
- `articulation-aware`：根据断奏、连奏等演奏标记给容忍范围。
- `rhythm-only`：不把按键时长纳入总分，仅展示数据。

v1.0 默认 `articulation-aware`。对没有足够记谱依据的目标时长，显示“参考值/低置信度”，不进行强处罚。

### 6.5 连续性、完成度与停顿

报告至少包括：

- 已覆盖目标音符比例
- 已完成小节比例
- 最长连续正确片段
- 主要停顿、重新进入位置
- 休止符遵守情况
- 用户主动暂停与演奏中断应尽可能区分

不要把练习中主动暂停误判为节奏失控；用户可以标记暂停，系统也可通过明显空白段提出确认。

### 6.6 总分与分项分

总分是可选摘要，不得掩盖分项：

- 音符准确度
- 起音准确度
- 节奏稳定性
- 按键时长
- 完成度/连续性

初始默认权重（允许按模式配置）：音符准确度 30%、起音准确度 20%、节奏稳定性 30%、按键时长 15%、完成度 5%。若某项未采集或低置信度，应重新归一化有效权重，并明确展示；不能把“无数据”当 0 分或 100 分。

## 7. 练习模式与策略配置

所有模式必须复用同一 Rust Core 和指标实现，通过 `PracticeProfile` 配置改变容忍窗、纳入分数的指标和练习策略，不得复制多套评分代码。

### 7.1 模式清单

1. **自由演奏/录制**：记录事件和时间线，不强制给分。
2. **音符准确度**：重点关注错音、漏音、额外音。
3. **节奏稳定**：弱化音高错误对节奏结果的影响，强调 IOI、局部速度、漂移。
4. **按键时长**：专门训练物理按键时长；无可靠 Note Off 数据时禁用该模式。
5. **慢速练习**：以较低目标速度计算目标时间，所有目标时间基于练习 tempo map。
6. **分段循环**：选择起止小节，循环练习；报告既可按每轮，也可汇总多轮。
7. **渐进提速**：达到稳定门槛后逐步提高速度；失败时回退，不无限自动提速。
8. **左右手/声部单练**：按谱面 part/staff/voice 过滤，不根据 MIDI 通道臆断。
9. **双手合练**：在同一时间轴上计算各声部和协调偏差。
10. **历史对比**：比较相同乐谱区域在不同日期/速度下的表现。
11. **视奏/未知起始位置（基础版）**：用户指定起始小节；自动识别重复段落可列为后续能力。
12. **踏板观察**：展示 CC64 时间线；只有谱面和设备能力充分时才给正确性评分。

### 7.2 PracticeProfile

至少包含：

- `profileId`、`version`、`displayName`
- `targetTempoBpm` / `tempoMapOverride`
- `selectedParts` / `selectedStaves` / `selectedVoices`
- `startMeasure` / `endMeasure` / `loopCount`
- `enabledMetrics`
- `onsetToleranceMs` / `pitchToleranceSemitones`
- `durationPolicy`
- `scoreWeights`
- `autoTempo.enabled`、`stepBpm`、`passThreshold`、`requiredConsecutivePasses`、`maxTempoBpm`、`fallbackBpm`
- `pauseHandlingPolicy`
- `latencyCalibrationId`

所有配置必须可序列化、可保存，并在报告中记录当时配置快照。

## 8. 诊断与练习建议

系统不应只说“节奏 72 分”，而应把分数转换为证据和动作。

每条诊断至少包含：

- `diagnosticId`
- `category`：global-offset / local-jitter / tempo-drift / missed-notes / extra-notes / pitch-errors / duration / rest-violation / low-confidence
- `severity`
- `measureRange` / `beatRange`
- `evidence`：指标、样本数、实际值、目标值
- `confidence`
- `suggestedAction`
- `sourceEventIds` / `scoreEventIds`

建议规则示例：

- 整段都晚约 40 ms，但 IOI 稳定：提示检查输入延迟/起拍，不要误报为忽快忽慢。
- 前半段偏快、后半段偏慢：提示分段节拍器练习，不能因为总时长相同而判稳定。
- 速度比连续多个窗口上升：提示渐慢（实际越来越慢）；连续下降则提示渐快。方向定义必须在 UI 中一致。
- 某小节抖动显著高于前后小节：优先推荐该小节循环练习。
- 音符正确但释放普遍过早：切换到按键时长模式。
- 事件配对质量低：优先排查 MIDI 设备/适配器，不应要求用户先练琴。

v1.0 先使用确定性规则生成诊断。AI 解释层可以后加，输入只能是结构化诊断证据，必须保留原始指标与来源。

## 9. 报告与交互要求

### 9.1 总览

展示：

- 总练习时长、目标速度、实际演奏覆盖率
- 分项分数与置信度
- 整曲节奏稳定性摘要
- 全局偏早/偏晚
- 最差 3 个小节/片段
- 本次最值得练习的 1–3 个片段
- 与上次相同区域的趋势（有历史数据时）

### 9.2 乐谱/时间线联动

- 点击小节可显示目标与实际事件。
- 每个音符至少能看到：目标拍位、目标起音、实际起音、偏差、音高匹配、实际按键时长、配对状态。
- 可在时间线上显示目标节拍线、实际起音线、Note On/Off、踏板事件。
- 鼠标悬停/键盘聚焦都能查看诊断，不得仅靠颜色传达信息。
- 支持将某个区间加入循环练习。

### 9.3 历史与导出

- 会话元数据：乐谱指纹、设备来源、适配器版本、Core 版本、算法版本、Profile 快照、校准记录。
- 导出 JSON 报告；CSV 可作为后续增强。
- 历史对比只比较兼容的乐谱指纹、相同或可解释的目标速度/模式。配置不同必须标注，不能直接声称分数可比。

---

## 10. 置信度、错误状态与数据质量

置信度不是一个神秘数字，应说明原因。至少考虑：

- MusicXML 解析完整度
- MIDI 丢包/队列溢出/未知事件
- Note On/Off 配对成功率
- 对齐歧义比例
- 可用样本量
- 时钟/延迟校准状态
- 当前指标是否适用于所选模式

当事件队列溢出或输入丢失时：

- 必须产生显式 `dataDegraded` 状态和计数。
- 不得静默丢弃后仍输出看似精确的结果。
- 受影响的指标应标记低置信度或不可评分。
- 报告保留原始错误信息，供复现与排查。

## 11. 核心架构与模块边界

### 11.1 数据流

`Device Adapter → Raw MIDI Trace → MIDI Normalizer → Key Lifecycle / Pedal State → Score Parser → Alignment → Metrics → Scoring → Diagnostics → Practice Plan → UI`

乐谱解析和 MIDI 采集可并行，但最终报告由 Rust Core 基于固定输入与配置生成。

### 11.2 Rust Core 模块

建议模块：

- `score_model`：ScoreEvent、tempo map、乐谱能力标记
- `midi_protocol`：原始包与规范化事件
- `key_lifecycle`：Note On/Off 配对与质量标记
- `pedal_state`：CC64 状态区间
- `alignment`：目标与实际事件匹配
- `metrics::pitch`
- `metrics::onset`
- `metrics::rhythm`
- `metrics::duration`
- `metrics::continuity`
- `scoring`：Profile 权重与有效项归一化
- `diagnostics`：可追溯规则诊断
- `practice_plan`：基于诊断生成练习建议
- `session`：会话、事件序列、版本和数据质量
- `replay`：确定性回放与快照测试
- `report`：稳定的 JSON 输出契约

### 11.3 进程与并发

- 每个会话由单一顺序处理器负责事件排序与状态变更。
- 当前规模不需要为了“高并发”而强行拆分线程。
- 采集线程/回调只做最小解析和入队；核心按顺序消费。
- 若有界队列满，必须记录溢出并降级当前会话。
- Rust Core 是唯一评分事实来源。前端可以显示暂定状态，但不得复制一套独立算法生成最终分数。

### 11.4 前后端接口

Rust Core 可先通过 WASM 在前端调用；如果设备/文件系统集成需要原生能力，再由 Node.js/Tauri 等外层负责。不要在 v1.0 为未确认需求同时实现 WASM、N-API 和独立服务。

建议对外接口：

- `parse_score(input, options) -> ScoreModel`
- `start_session(score, profile, metadata) -> SessionHandle`
- `push_midi_packet(session, packet) -> IngestResult`
- `finish_session(session) -> SessionReport`
- `replay_session(trace, score, profile) -> SessionReport`
- `validate_profile(profile) -> ValidationResult`
- `get_capabilities() -> CoreCapabilities`

接口需版本化；JSON Schema/Serde 类型应作为契约，前端类型从契约生成或校验，避免手工漂移。

## 12. 稳定性与可测试性要求

- 确定性：相同乐谱、原始事件序列、配置、Core 版本产生相同报告。
- 数值安全：处理空样本、除零、异常时间戳、负时长、溢出和浮点边界。
- 性能目标（初始参考）：普通 5–10 分钟曲目，数万条 MIDI/派生事件，在常规桌面设备上报告生成应保持交互可接受；正式性能门槛需以基准测试校准。
- 可观察性：记录 Core 版本、解析警告、输入异常、匹配原因和指标样本数。
- 可复现：任何报告中的诊断都应能回溯到对应 score event 与 performed event。
- 可扩展：新模式主要通过 Profile 和诊断规则组合，不复制评分算法。
- 隐私：默认本地处理；除非用户明确启用同步/云服务，不上传原始演奏事件或乐谱。

## 13. 验收测试（v1.0 必须通过）

### A. 总时长相同但节奏不稳

目标起音 ms：`[0, 500, 1000, 1500, 2000]`
实际起音 ms：`[0, 400, 1100, 1600, 2000]`

结束时刻相同，但局部间隔是 400、700、500、400 ms。报告必须指出局部忽快忽慢，不能判为稳定。

### B. 整体固定延迟但内部稳定

目标：`[0, 500, 1000, 1500]`
实际：`[40, 540, 1040, 1540]`

应显示整体晚约 40 ms，局部 IOI 基本稳定。不得仅凭全局偏差判定节奏不稳。

### C. 逐渐渐慢

目标间隔恒为 500 ms；实际间隔逐步增加，例如 `[500, 520, 545, 570, 600]`。应检测到速度趋势向更慢方向漂移，并指出涉及窗口/小节。

### D. 漏音与额外音

中间漏一个音或插入额外音时，后续正确音符仍需合理匹配，不能整体错位。漏音和额外音都要有明确事件记录。

### E. 时长与起音分离

两次演奏的起音完全相同，但 Note Off 不同；起音/节奏指标应相同，时长指标应不同。

### F. Note On velocity=0

必须被解释为 Note Off，正确关闭按键生命周期。

### G. 同音重复按键

同一 pitch 连续重复或重叠时，不能把两次演奏静默合并；无法唯一配对时标记 ambiguous。

### H. 踏板与按键分离

CC64 sustain 不得延长 `heldDuration`；按键时长只由 Note On/Off 决定。

### I. 数据质量降级

模拟队列溢出、丢失 Note Off、非法时间戳。报告应显式标记受影响指标低置信度/不可评分。

### J. 和弦容错

和弦内音符存在少量起音分散时，应按和弦簇分析完整度与离散程度，不应把和弦内各音误当作整段节奏加速/减速。

### K. 分段报告

选择第 8–12 小节后，所有汇总指标只统计该区间，并能列出最不稳定的小节；不得混入区间外数据。

### L. 权重缺失归一化

某次会话没有有效按键时长数据，不能把时长得分记为 0 或 100；其他有效分项权重重新归一化，并显示时长项“未评分”。

### M. 确定性回放

同一 trace、score、profile、Core 版本重复运行，报告的指标、匹配、诊断和分数完全一致（时间戳展示格式除外）。

### N. 渐进提速

只有连续达到配置的节奏稳定和音符准确门槛，才提高速度；失败时按策略回退或维持速度，并记录原因。

### O. 报告证据链

每条诊断至少能定位到 score event、performed event 或具体统计窗口；不能只输出没有证据的自然语言结论。

## 14. 实施阶段与交付物

### Phase 1 — 数据可信（必须先完成）

- 数据契约与版本号
- MIDI 规范化、velocity-zero Note Off
- Note On/Off 配对、重复音和异常事件处理
- 原始 trace 保存/回放
- MusicXML 基础解析与 tempo map
- 单元测试和契约测试

### Phase 2 — 可解释评分

- 对齐引擎与匹配原因
- 音高、起音、局部 IOI、节奏稳定性、时长、连续性指标
- 分段/小节报告
- 数据质量与置信度
- 上述 A–M 验收测试

### Phase 3 — 练习工作流

- 练习模式配置
- 分段循环、节拍器、慢速练习
- 渐进提速与失败回退
- 诊断转练习建议
- 历史对比与 JSON 导出

### Phase 4 — 体验增强（不阻塞核心）

- 更丰富的谱面视觉叠加
- 高级踏板分析
- 多设备适配器
- AI 解释层
- 自动识别重复段落、自动推荐片段等增强能力

每个阶段必须有可运行测试和演示样例，不接受只增加 UI 页面但核心结果不可验证的交付。

## 15. v1.0 完成定义

只有同时满足以下条件，才能称为 v1.0：

1. 核心评分完全由 Rust Core 负责，前端无第二套最终评分逻辑。
2. 有稳定、版本化的事件与报告契约。
3. 对齐可处理错音、漏音、额外音、和弦和部分异常输入。
4. 节奏指标能区分整体偏移、局部抖动、渐快/渐慢和前后补偿。
5. 起音与按键时长完全分离。
6. 每个分数有原始指标、样本数、置信度与证据链。
7. 无数据项不会被当作 0 分或满分。
8. 练习模式通过配置复用核心指标。
9. 验收测试 A–O 通过并可重复运行。
10. 有一份示例乐谱、模拟 trace、预期报告和运行说明。

**优先级原则：先把测量做可信，再把评分做可解释，最后才做 AI 教练和漂亮的 UI。**
