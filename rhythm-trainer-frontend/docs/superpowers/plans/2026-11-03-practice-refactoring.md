# 节奏训练器渐进重构实施计划

> 执行方式：使用 writing-plans 形成计划，后续使用 executing-plans 按任务实施。本文是待执行方案，不代表各模块已完成迁移。任务使用复选框记录进度。

**目标：** 在保持用户操作和评分口径的前提下，统一练习状态与时间，降低误判、会话卡住和修改功能时产生回归的风险。

**架构：** 保留 React 展示、电脑 Node 接入 MIDI 与执行业务、Rust 权威计划和评分。沿现有模块边界逐步拆分，不建立第二套评分或设备服务。

**技术栈：** React 19、TypeScript、Ant Design、Node ESM、WebSocket、Rust；保留现有 Capacitor iPad 壳。

**依据：** 用户确认的重构方向、[项目职责约束](../../../AGENTS.md)、[现有架构说明](../../development-architecture.md)。已有说明与最新行为有差异时，以代码、回归测试及用户最近确认的规则为准；对应文档应在实施时同步修正。

**日期：** 2026-11-03。以下代码路径均相对 `rhythm-trainer-frontend/`。

## 1. 决策与范围

需要重构，优先级高于全量 TS 迁移。类型系统帮助发现接口错误，但不能替代状态设计、运行时校验和评分回归测试。

本次路线不是整体重写：

- 不迁移为纯浏览器应用；电脑继续接琴、运行后端，iPad 负责展示和控制。
- 不重写 Rust 判定算法，不修改版本、指纹及可信度约束。
- 不再更换 UI 库，不同时重做页面视觉。
- 不先把全部 `.mjs` 改成 `.ts`；在拆分模块时引入 TS。
- 不把已有模块重新复制一遍；先确认其职责、扩展点和调用链。
- 内容生成的教学改进另行验收，不混入“行为保持不变”的结构重构。

## 2. 当前证据与问题

已审查的核心文件是 `server/engine-server.mjs`。它承担协议处理、会话资源、输入接纳、暂停区间、实时反馈、结算及保存编排，修改容易跨越多个状态所有者。

最近已用真实 Node＋Rust 协议测试复现并修复：

1. 多次暂停后，最终评分按原始目标时间比较后续暂停边界，导致漏算顺延。
2. 重复暂停／继续直接进入内核，触发非法状态转换。
3. 倒退的暂停时间先改变协调器状态，再被评分内核拒绝，造成状态不一致。

这些修复应成为重构前的保护测试，不能在拆分时丢失。它们不证明其他路径没有问题，也不证明所有暂停边界与 Rust 游标语义已经完全一致。

已有可复用基础：

| 模块 | 现有职责 | 重构要求 |
| --- | --- | --- |
| `server/session-clock.mjs` | 首键捕获时间到会话时间映射 | 保留并扩展边界，不用消息到达时间替代 |
| `server/song-completion.mjs` | 曲目结束边界与暂停顺延 | 保留模式差异，不顺手扩大自动结束范围 |
| `server/live-note-feedback.mjs` | Rust 对齐结果的实时展示 | 不升级为另一套评分器 |
| `server/take-finalization.mjs` | 冻结记录、保存、幂等重试 | 继续复用，不另写保存服务 |
| `server/midi/` | 设备适配、解码、时钟和捕获 | 在现有结构内整理接纳边界 |
| `server/training/phrase-strategy.mjs` | 练习乐句策略 | 先审查已有实现，不再从零创建生成器 |
| `src/features/practice/` | 前端会话、选段、试听关联和归位控制 | 扩展现有控制器，减少 App 编排 |

## 3. 必须保留的用户行为

- 判定线由用户点击“开始练习”才开始倒数和推进。进入页面、换曲或修改配置不自动开始。
- 读谱与跟手的等待起奏行为保持现有策略，不与判定线强行合并。
- 无输入不能判绿；错音、多按音和和弦缺音保留各自证据。
- 暂停时不推进判定；继续不新建 Take，也不重复累计暂停。
- 选音符、换模式、换曲必须按既有顺序处理旧 Take，不能丢弃尚未保存的数据。
- 待弹但未起奏的记录保持现有 standbyOnly 审计规则，不伪装成已练习的零分成绩。
- 不因改名或拆分改变循环续轮规则。自动开始与自动结束是独立策略。
- 顶部和底部控制栏由轻点空白切换，显示后不计时自动隐藏；按钮操作和滚动不误触切换。
- 手动翻谱后可以自由浏览，点击“回到当前”或正确演奏按既有规则恢复跟随。
- 多设备／标签页不能同时占用同一演奏输入；明确拒绝，不静默抢占。

## 4. 状态归属与依赖

```text
页面与按钮
  → 前端练习控制器（命令、请求状态、服务端状态投影）
  → WebSocket 协议边界（校验、路由、错误返回）
  → 后端会话编排（唯一资源所有者）
      → MIDI 输入接纳与时间映射
      → Rust 会话协调器／计划／评分
      → Take 结算保存服务
  → 后端事件返回前端
```

| 数据 | 所有者 | 其他模块如何使用 |
| --- | --- | --- |
| 生效的练习配置与计划 | 后端已验证的冻结快照 | 前端草稿确认后请求，过期响应不可覆盖新请求 |
| 当前 Take、设备租约、会话资源 | 后端会话编排 | 页面只发送命令、接收状态 |
| 评分状态与判定 | Rust 内核 | Node 调用，前端展示 |
| 捕获时钟、首键起点、暂停区间 | 后端会话时间模块 | 向反馈、结算、结束策略提供统一数据 |
| 保存状态与重试草稿 | `TakeFinalizationService` | 会话编排订阅结果，不重新计算成绩 |
| 工具栏、设置草稿、手动翻谱 | 前端 UI／已有功能控制器 | 不反向改写权威评分时间 |

“唯一所有者”不意味着再增加一个与 Rust 并列的评分状态机。Node 管理资源和协议生命周期；Rust 管理内核状态；前端是服务端状态的投影。实现时需明确映射，不维护三份独立可写状态。

## 7. 后续阶段的具体边界

### P2：会话生命周期

从 `engine-server.mjs` 提取会话编排，组合现有协调器。开始需先验证计划和参数，再占用资源；所有失败路径释放本次创建的资源。结束需要区分用户结束、自然完成、取消待弹和断连。固定线／Follow 使用不同推进策略，共享资源释放和保存协议，不能强迫两者共用评分模型。

重点验证：开始过程中取消、连续换曲、旧计划响应晚到、两个标签页竞争、断连后下一次开始。

### P3：MIDI 输入

扩展 `server/midi/`，把入口中的接纳规则抽成明确模块。保留 captureEpoch、sourceSeq、捕获时钟、按下／松开和踏板证据。所有传输共用接纳入口，不为了“无报错”删除异常证据。

重点验证：重复消息、旧轮输入、乱序、设备拔插、暂停期间消息、和弦多按／漏按、同音重按、持键后断连。模拟协议通过不能代替真实琴和 iPad 实机测试。

### P4：结算保存

保留 `TakeFinalizationService`，抽取调用它之前的结算编排。停止采集、封存证据、Rust 结算、持久化及派生更新顺序需明确。保存失败保留冻结草稿，重试不重新评分；派生更新失败不谎报 Take 丢失。

重点验证：重复结束、断连与结束竞态、磁盘失败、跨连接重试、历史格式兼容。进程崩溃后能否恢复未落盘草稿另立需求，不能把内存重试宣称为崩溃恢复。

### P5：前端控制

优先整理已有 `usePracticeSession`、`useScorePick`、`useRoundReturn`，再减少 `App.tsx` 编排。复用 `PracticeSessionControls`、`PerformanceToolbar`。服务端状态和界面草稿分开，不能用本地动画状态决定成绩或是否已保存。

重点验证：暂停后选音符、切模式、保存失败重试、工具栏轻点切换、手动翻谱恢复、横竖屏、安全区域和谱面滚动。对评分无关的样式调整只做必要验证。

### P6：生成器

先审查现有 `phrase-strategy`、`skill-drills`、`fundamental-drills` 及 `training-service`。结构重构保留现有输出；教学改进另建变更任务。

教学改进应定义：训练目标、难度约束、拍号与节奏词汇、乐句长度、休止与收束、音域和声部、重复与变奏比例。随机种子用于复现，不能让每个音都独立抽样。由目标练习时长与速度推导合理长度，再结合乐句边界，而非只增加音符数。

重点验证：相同种子可复现、不同种子有合理变化、每小节时值合法、音域与难度符合配置、预览与正式开始使用同一份冻结谱面。自动检查加人工音乐审阅，不用“生成成功”代表训练有效。

## 9. 发布、回退与完成定义

- 每阶段独立可运行、可验证、可回退，不用一份巨大提交覆盖六个阶段。
- 优先保持协议和历史记录格式；确需改格式时另写兼容方案和旧数据读取测试。
- 在隔离数据目录启动测试后端，禁止用用户正式练习记录进行故障注入。
- 当前练习尚未结束时不直接重启生产开发服务；代码已修改与运行服务已生效分别说明。
- 回退代码不能删除用户记录或回滚已生成的真实成绩。
- 类型检查通过不是验收完成；需有真实协议链结果，以及明确的实机验证范围。

最终验收看可靠性和职责清晰度，不以文件数、行数或 TS 覆盖率为目标。第一阶段完成后再评估后续优先级，避免为重构而重构。

## 10. 实施记录：第一阶段首批拆分

本批新增 `server/practice/pause-ledger.mjs` 与独立测试，并将计时练习入口接入它。账本拥有会话时间、暂停起点、源时钟暂停区间、会话暂停区间和接纳阶段编号；读取区间得到副本。原生内核成功执行后才提交账本。

### 状态与命令约定

## 12. 实施记录：启动后异常与断连清理

## 15. 实施记录：计时 MIDI 接纳账本

## 16. 设备重连、资源与超时审查（2026-11-03）

### 已复现并修复

1. **旧端口回调混入新连接。** 原生 openInput 的回调原本在到达时读取当前 connection；旧端口的迟到回调可能因此被赋予新 generation 和 sourceId。现在回调捕获打开时的 generation，并在入口核对当前连接，过期回调直接计入 staleGenerationDropped。回归先复现旧音 60 和新音 64 同时出现，修复后只接纳新音，且新连接 sourceSeq 从 1 开始。
2. **WebSocket 状态监听泄漏。** 每次连接添加 takeHealthHandler，却未调用 onStatus 返回的注销函数。新增 connection-status 生命周期绑定，socket close 时立即注销。500 次连接关闭模拟后监听数回到零，关闭的监听不再收到状态事件。
3. **Follow 重连掩盖本轮断连。** 结束时只读取设备当前健康状态会抹掉中途断连。现在上下文保留本轮最差健康状态，断连／降级不会因恢复连接而升级为可信。真实 Node＋Rust 协议已验证断开、重连、继续完成后仍报告 disconnected 和 trustworthy=false。
4. **结束后的计时缓存保留。** 正常结算与失败清理现在均释放 ingests、rawNotes、接纳账本和评分序号映射；已冻结的保存草稿仍由持久化服务持有，不能为了省内存丢失待重试记录。

### 长时间资源边界

- 适配器默认队列 2048、trace 5000，已有明确上限和溢出计数。持续 16000 条模拟消息验证队列可排空、trace 保持配置上限。
- Follow 输入证据最多保留 20001 项（含截断检测哨兵），performedMidi 最多 100000 项；达到上限的标志必须继续写入结果。
- 活动中的 Timeline ingests、接纳索引及实时对齐证据仍随事件数增长。适配器 trace 有界不代表整轮评分内存有界；当前尚未施加会静默删掉评分证据的截断。
- 原生失联句柄 zombieHandles 为避免既有 WinMM 崩溃而保留，反复拔插仍可能增加资源占用。不能直接删引用或强行 close；后续需验证后端安全释放能力，或单独设计设备子进程重启与证据边界。
- 本批没有给出固定“可连续练多少小时”的承诺，也未做真实电子琴／iPad 插拔实测。

### 测试为何超时

超时来自 phrase-strategy 的批量回归，并非练习网络请求。原单用例同步执行 10 类练习 × 3 等级 × 3 种子，含 XML 生成／导入、Rust 计划构建和指纹校验，统一受 15000 ms 墙钟预算约束。已有日志显示并发全量时约 16500 ms，单独复跑约 4235 ms，降低全量并发后也通过；这些证据支持负载竞争，但没有 CPU profile，不能据此断言具体热点。

现在按练习类型拆为 10 个独立参数化用例，每项仍验证全部 9 个等级／种子组合，保留原 15 秒限制和全部断言。相关测试中每类约 0.36–0.66 秒；没有扩大超时或删除困难样本。全量验证结果以本批运行日志为准。

追加验证：默认并发全量下，生成器拆分用例全部通过，但 AppShell 的 ScoreViewer 动态导入测试超过 5000 ms。这表明负载敏感不只发生在生成器。将 `npm test` 默认设置为 `vitest run --maxWorkers=2`，限制同时运行的工作进程；保持原有测试时限与覆盖。该设置属于测试调度，不改变生产练习性能。首次全量的这次额外超时应保留记录，不隐藏为一次全绿。

## 19. 实施记录：资源测量与评分证据完整性边界（2026-11-03）

§17 留下的优先项是“定义资源测量与评分证据完整性边界”，本批只补测量与边界证据，不改变上限数值、不缩短保留时间。

### 现状核对

- `TakeResourceBudget` 早已按事件数与序列化字节数约束单轮输入（默认 100000 事件 / 32 MiB，事件上限可用 `RHYTHM_TAKE_EVENT_LIMIT` 调整），溢出时不做静默截断：`admitResourceEvent` 拒绝当前包、写入 `resource_limit` 日志并调用 `finishSession({ interrupted: true, endReason: 'resource_limit' })`。
- 溢出轮次已经标记为 `endReason=resource_limit`、`trustworthy=false`，健康状态降为 `degraded`，因此 `scoreStatus=DEGRADED`。问题是记录里没有测得的用量、实际上限和被拒绝的包，无法审计“证据在哪里停止”。

### 本批改动

- `TakeResourceBudget.snapshot()` 返回只读测量：`eventLimit`、`byteLimit`、`events`、`bytes`。
- `admitResourceEvent(payload, kind)` 记录溢出证据：`rejectedKind`（raw-midi / hit / note / pause）、`rejectedSourceId`、`rejectedSourceSeq`、`rejectedAtSessionMs`；被拒绝的包不进入 `ingests`、不进入接纳账本，也不占用预算。
- 保存记录与实时报告新增 `captureDiagnostics.resourceBudget`：上限、已用事件/字节、`reached` 和上述拒绝证据。新轮次开始时与计数器一起清零。
- 未改变：上限数值、Follow 的独立输入上限、`resource_limit` 的结算路径与历史格式（新增字段为 additive）。

### 验证

- 真实 Node＋Rust 超预算用例：第 101 个包触发 `resource_limit`，记录 `events=100`、`rejectedSourceSeq=101`、`rejectedKind='raw-midi'`、`scoreStatus=DEGRADED`；随后新轮次 `reached=false`、`events=0`，可正常保存。
- `server/practice`、`armed-start.api`、`follow-protocol`、`take-persistence` 共 66 项通过；`npm run selftest` 251 项通过；`npm run typecheck:server` 通过。
- 仍未做：长期运行的真实内存测量、100k 事件上限下的完整评分耗时、把上限按设备/曲目调优。当前只能声明“单轮输入有界且溢出可审计”，不能声明内存占用已优化。
