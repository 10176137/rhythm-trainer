# Rhythm Trainer 前端设计思路与实现边界

版本：0.1.0  
当前默认练习：乐谱跟练 / 72 BPM / 双手 / 实时反馈  
技术基线：React + TypeScript + Vite

## 1. 产品目标

Rhythm Trainer 不应只是一个“按对音符就加分”的 MIDI 测试器。长期目标是形成可解释、可验证的钢琴练习闭环：

1. **观察表现**：采集按键音高、按下/抬起时刻、力度，以及设备和计时状态。
2. **对齐乐谱**：把真实演奏事件与标准化乐谱目标对应起来。
3. **评价问题**：区分错音、漏音、多余音、过早/过晚、节奏不稳、时值不符、双手协调问题等。
4. **提供训练动作**：例如降低速度、分手、循环小节、突出细分拍、针对难点练习。
5. **验证是否掌握**：重新测试原段落，并通过相似新题与延迟复测避免把“重复记住了”误当成真正掌握。

前端的职责是呈现状态、收集操作、可视化证据与反馈；不应自行复制一份生产评分算法。时间对齐、评分和诊断最终由 Rust Core 或明确的引擎接口负责。

## 2. 首期范围与非目标

### 首期需要有

- 统一练习工作台，而非每种模式复制一套页面。
- 模式切换及每个模式的能力声明。
- 练习配置：BPM、练习手、反馈方式、小节范围等。
- 会话控制：开始、暂停、继续、结束、重新开始。
- 乐谱视图与当前目标提示。
- MIDI 设备输入及虚拟键盘模拟输入。
- 实时反馈消息与基础会话统计。
- 将来可替换的 Rust 引擎桥接层。

### 首期不应假装已经完成

- 完整 MusicXML 解析、复杂记谱（连音线、附点、三连音、声部等）的正确对齐。
- 专业乐谱排版和自动翻页。
- 经过校准的设备延迟补偿、精确节拍调度和高可信度时值评估。
- 完整的钢琴教学诊断、学生能力模型或大模型教师。
- 音色、坐姿、手型、触键质量等仅靠 MIDI 无法可靠得出的结论。

目前的示例谱、简单事件匹配和模拟键盘只用于开发 UI 流程，不代表正式算法结果。

## 3. 交互设计原则

### 3.1 一个工作台，多个训练模式

用户进入练习页后应始终认识同一套主区域：

- **左侧/上方：模式与曲目**：选择要练什么，以及要练哪一段。
- **中央：乐谱与当前目标**：视觉焦点，提示正在演奏的位置和接下来的目标。
- **底部/中央偏下：练习控制条**：开始、暂停、继续、结束、节拍器及速度。
- **右侧/下方：实时反馈**：显示发生了什么、证据是什么，以及下一步建议。
- **状态区域：设备和引擎状态**：明确区分 MIDI 已连接、正在采集、引擎可用、练习进行中等状态。

不同模式只在必要部分显示特定设置。例如自由弹奏可以不要求乐谱；乐句循环需要起止小节；分手练习需要选择左手/右手。不要在全局页面里塞满所有模式的配置。

### 3.2 反馈要“有证据”，避免武断

一条反馈应区分：

- **观察事实**：例如“目标音为 MIDI 60，输入音为 MIDI 62”。
- **评估结论**：例如“当前目标音不匹配”。
- **原因假设**：例如“可能是看谱定位错误”，需要足够证据与置信度才能呈现。
- **建议动作**：例如“单独练习这一拍，并将速度降至 60 BPM”。

数据质量不足时要提示“无法可靠判断”，而不是硬给学生贴上错误原因。初版实时反馈应该少而清晰，避免每个事件都弹出打断演奏的提示。可将严重错误即时显示，复杂总结留到段落结束。

### 3.3 运行状态永远可见

需要明确标识当前处于待开始、倒数、练习中、已暂停、处理中、已完成或发生错误。设备断开、事件时间戳异常、乐谱未加载、引擎不可用时，界面应有可理解的提示，而不是静默失败。

### 3.4 切换模式不能破坏数据

- 未开始：可以直接切换模式。
- 练习中：建议先暂停或结束，确认后切换，避免会话状态不一致。
- 已完成：保存结果，然后创建新的会话。
- 模式切换不应重连 MIDI 设备，也不应删除原始 MIDI 事件日志。
- 曲目或小节范围变化时，必须重新生成目标事件和对齐状态。

## 4. 模式配置与模式策略分层

模式注册表只描述静态能力，不等于全部行为逻辑。建议按三层拆分：

1. **ModeDefinition（配置元数据）**：标题、分类、是否需要乐谱/MIDI、允许的设置项、是否允许实时反馈。
2. **ModeStrategy（模式策略）**：如何确定练习目标、是否循环、手部过滤规则、完成条件、支持哪些评价维度。
3. **PracticeSession（会话生命周期）**：开始/暂停/恢复/结束，事件收集，数据归档与通用错误处理。

新增一个模式时，按需实现策略，不要复制整个工作台，也不要把评分算法放入模式组件。

| 模式 | 核心目标 | 模式专属配置 | 复用能力 |
| --- | --- | --- | --- |
| 节奏训练 | 拍点、节奏比例与稳定性 | 节拍细分、节奏型 | MIDI、节拍器、评估结果 |
| 乐谱跟练 | 将演奏与乐谱目标对齐 | 曲目、BPM、练习手 | 乐谱视图、实时反馈、会话控制 |
| 分手练习 | 隔离手部难点 | 左手/右手/回到双手 | 曲目、评估、练习记录 |
| 乐句循环 | 练习指定片段 | 起止小节、循环次数、目标速度 | 乐谱定位、会话控制 |
| 自由弹奏 | 采集和回看演奏 | 录制/回放选项 | MIDI 事件日志、设备状态 |

## 5. 前端架构

```text
React App / AppShell
└── PracticeWorkspace
    ├── ModeSelector          模式选择
    ├── PracticeSettings      当前模式适用的设置
    ├── ScoreViewer            乐谱展示与光标
    ├── PracticeToolbar        开始/暂停/结束、节拍器
    ├── PerformanceSummary     命中、漏音、时序等摘要
    └── FeedbackPanel          实时反馈与训练建议

Domain / Application Layer
├── modeRegistry              静态能力定义
├── modeStrategies            各模式的目标与规则
├── practiceSession           会话状态机与合法转换
├── scoreNormalizer           MusicXML -> 标准化目标事件
├── midiAdapter               设备事件适配
└── engineBridge              对接 Rust Core

Rust Core
├── 事件规范化与时间校验
├── 乐谱-演奏对齐
├── 特征提取
├── 评分与错误分类
├── 诊断证据与置信度
└── 训练建议与复测策略
```

推荐目录逐步演进为：

```text
src/
  app/                    # AppShell、路由、全局布局
  components/             # 可复用纯 UI 组件
  config/modeRegistry.ts  # 模式元数据
  features/
    practice/             # 会话控制与配置
    modes/                # 模式入口和专属设置
    score/                # 乐谱加载、光标、定位
    midi/                 # MIDI 设备与事件
    feedback/             # 反馈列表、严重程度、建议动作
    history/              # 会话结果与复测记录
  services/
    engineBridge.ts       # Rust/WASM/本地服务接口
    practiceRepository.ts # 本地或后端存储适配
  types/                  # 跨层领域 DTO
```

当前起步项目有意保持较少文件：工作台逻辑集中在 `App.tsx`，便于先看清流程。随着真实 MIDI、Rust 接口、MusicXML 和历史记录加入，应优先拆出 `usePracticeSession`、`engineBridge` 和各功能组件，避免 `App.tsx` 膨胀。

## 6. 会话状态机

会话状态推荐定义为：

```text
idle -> countdown -> running <-> paused
running -> processing -> completed
running/paused -> cancelled
任意活动状态 -> error（可恢复错误应保留已采集事件）
```

当前原型简化为 `idle / running / paused / completed`。正式版本再加入倒数、分析中、取消和错误态。

状态切换应集中到 session controller，而不是按钮各自修改多个布尔值。避免出现 `isRunning=true` 与 `isPaused=true` 同时成立之类的非法组合。结束会话时先停止事件采集/调度，再生成结果，最后保存记录；暂停时保留会话和设备连接，不应重新启动另一轮计时。

## 7. 事件流与时间准确性

正式练习流程应是：

```text
MIDI input
  -> 统一事件格式（来源、单调时间戳、note-on/off、音高、力度）
  -> 输入健康检查（丢失、乱序、重复、时间异常）
  -> Rust Core
  -> 对齐目标音符及计算特征
  -> 返回带证据和置信度的评价结果
  -> React 更新光标、反馈面板和摘要
  -> 归档原始事件与结果，支持回放复算
```

关键约束：

- 目标音符的预定时间应由绝对单调时钟和拍点时间线计算，不要用不断累加的 `setTimeout` 构造音乐时间线。
- 设备延迟校准与用户演奏本身的抢拍/拖拍偏差必须分开建模。
- `note-on` 与 `note-off` 都有意义；仅对比音高无法评价音符时值或断奏/连奏。
- 记录原始事件，可使用同一组事件做确定性回放和算法回归测试。
- 若时钟或对齐质量不够，应降低置信度或不输出诊断，而不是伪造精确结论。

## 8. UI 与状态管理建议

- **React**：组件和视图组合。
- **TypeScript**：模式、事件、会话与反馈 DTO 的静态类型。
- **Vite**：开发服务器与构建。
- **Zustand（建议后续引入）**：跨组件共享的练习配置、设备状态与会话状态。当前原型规模还小，可以先用组件状态，不必提前增加依赖。
- **TanStack Query（有后端后引入）**：曲目、用户记录等远端数据；它不应负责 MIDI 实时事件流。
- **SVG/专用乐谱渲染方案**：当前 SVG 适合示意与高亮，正式五线谱建议使用专业记谱渲染器或由标准化乐谱数据生成的 SVG。

实时 MIDI 事件应避免每个事件都导致整个大页面重渲染。事件先进入轻量队列/控制器，再以适当频率更新可见 UI；高频原始数据和历史日志不要直接塞入所有组件的 React state。

## 9. Rust Core 的接入边界

建议定义稳定的 TypeScript DTO，让前端与 Rust 之间交换数据，而不是让前端依赖 Rust 内部数据结构。例如：

```ts
export interface ScoreTargetEvent {
  eventId: string;
  midiNote: number;
  onsetMs: number;       // 相对练习时间线的目标时刻
  durationMs: number;
  hand: 'left' | 'right';
  measure: number;
}

export interface EvaluationResult {
  eventId?: string;
  category:
    | 'hit' | 'early' | 'late' | 'wrong_pitch'
    | 'missed' | 'extra' | 'duration_mismatch'
    | 'timing_unreliable';
  errorMs?: number;
  confidence: number;
  evidence: string[];
}
```

以上是接口设计示例，不意味着当前 Rust Core 已实现这些完整字段。适配层建议暴露 `startSession`、`pushPerformanceEvent`、`pauseSession`、`resumeSession`、`finishSession` 和 `replaySession` 等明确方法。生产评分逻辑只有一份；React 里的简易比较仅用于原型演示。

部署方案取决于产品形态：浏览器网页可以考虑适配为 WebAssembly 的核心子集，或通过本地服务/桌面宿主调用 Rust 原生模块。Node.js N-API 模块不能直接当作浏览器模块导入。

## 10. 视觉方向

视觉风格应服务练琴，而不是像数据后台一样塞满指标：

- 中央乐谱区拥有最高视觉优先级；当前小节、当前拍和错误音符需清楚但克制地高亮。
- 练习控制条应在演奏时容易操作，关键按钮不应因滚动而丢失。
- 反馈用稳定的颜色和图标表达状态，但不能只靠颜色区分；配合文字和位置。
- 设备和引擎状态与学生成绩分离。连接失败不能显示成演奏错误。
- 实时反馈控制信息密度：当前事件及时提示，复杂分析在乐句/练习结束后汇总。
- 小屏幕可将左右栏改为折叠面板，但不要让乐谱与关键反馈互相遮挡。

## 11. 验收标准

### 前端流程

- 初始默认值为乐谱跟练、72 BPM、双手、实时反馈；默认乐谱为 4 小节 C 大调钢琴练习曲，采用纯净谱面 + 绿色当前拍高亮。
- 五种模式均可从注册表展示并切换。
- 开始、暂停、继续、结束行为符合状态机，练习中不会悄悄丢失事件。
- 模拟键盘可在无真实设备时验证主要交互。
- MIDI 连接失败、权限拒绝、设备断开均有明确状态提示。
- 模式切换不会创建重复 MIDI 监听器或残留旧会话的闭包状态。

### 真实评分接入后

- 同一段原始事件回放能得到确定一致的评价结果。
- 目标计划不受定时器累积漂移影响。
- 对 note-on/off 分开验证，覆盖持续时间与重叠音符。
- 评价项覆盖早/晚、错音、漏音、多余音、时值、双手协调等核心类别。
- 低质量输入可返回不确定/数据不足，而非输出虚假的精确诊断。
- 规则/算法变更有固定测试用例和回归测试。

## 12. 建议开发顺序

1. **稳定 UI 会话骨架**：抽离 `usePracticeSession`，严格约束开始/暂停/恢复/结束转换。
2. **事件契约先行**：确定 `ScoreTargetEvent`、`PerformanceEvent`、`EvaluationResult`，写接口测试。
3. **时间线和节拍器**：基于单调时钟和绝对目标时刻，先验证时间准确性。
4. **MusicXML 导入**：把乐谱转成标准化目标事件，并单独测试复杂记谱。
5. **Rust Core 桥接**：替换 React 内的演示评分逻辑，UI 只呈现引擎结果。
6. **练习报告**：显示证据、错误分布、稳定性趋势与可执行的下一轮练习建议。
7. **教师闭环**：加入针对性练习、相似新题、延迟复测和掌握度模型。

## 一句话总结

先把 Rhythm Trainer 做成“稳定的练习会话平台”，再不断增加模式和教学策略。模式注册表解决可扩展性，统一会话状态机解决可靠性，Rust Core 保证评价只有一个权威实现，反馈系统负责把评价变成可以验证的下一步练习。
